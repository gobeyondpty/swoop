## What changed

All existing public provider entry points admit the SDK's shared routing policy,
including Deals, Explore and all three Hotels functions. The consumer consults
SDK capability metadata rather than maintaining a second endpoint list. Unknown
entry points retain real legacy proxy/failover behavior. Callers need no request
or response contract change.

The policy prefers native IPv6, reuses healthy mia1 connections during cooldown,
and permits one recovery probe. Health is shared across Google endpoints, with
30/60/120/240/300-second cooldowns, positive jitter, Retry-After, generation checks,
bounded concurrency and state. Flight replay retains identical bytes/headers;
session failover bootstraps the chosen route and rebuilds from original inputs.
Session jars are isolated by route/service/POS/currency and leased for a complete
transaction. Explore params belong to the particular cookie jar, not a proxy URL
whose client might have been evicted. Per-origin Deals workers retain isolated
jars. No request observer, cancellation event or tenant state is cached.

There is one enclosing deadline through staged/fan-out/session work. HTTP caps
and initial proof caps remain endpoint-appropriate: 2 seconds for flight RPCs,
5 seconds for session bootstrap plus first RPC. The first session benchmark
showed a valid Deals stream took about 3 seconds, so a 2-second session proof
would misclassify ordinary latency. Parsed hotel RPCs release the proof cap for
remaining session work, without extending the attempt or enclosing deadline.
Valid protocol empty inventory stays healthy. Malformed or ambiguous framing
cannot silently become an empty Deals result. Ambiguous comparisons remain
bounded; invalid arguments and detailed outages are not classified as blocking.

## Connectivity and timeout cause

vin1 IPv6 **can connect and return real inventory**. A failure to complete a
particular Google RPC does not establish loss of IPv6 connectivity. Native
AF_INET6 connects to Google port 443 and mia1 SOCKS connects are retained in
`native-connect.json`. Curl is not the shipped transport.

The earlier production health evidence is retained in `historical-health.json`:
GetCalendarPicker `http_redirect`, GetShoppingResults `timeout`, fallback closed
and healthy. Historical calendar/shopping tails were 8141.6/3182.6 ms. Subsequent
successful probes do not invalidate that evidence; failures are intermittent.

Earlier isolated diagnostics at evidence SHA
`9178845093f8f39e5765db3dc6bd783b89ca4f23` found fast TCP/TLS followed by compact
gRPC 13 or RPC timeouts, with both native and curl clients and both vin1 address
families, while the matched mia1 route returned inventory. This supports an
egress-dependent Google refusal. It does not distinguish rate shaping, reputation,
session trust or backend behavior. There was no HTTP 429, Retry-After or explicit
rate-limit/interstitial evidence establishing throttling. Some timeouts occurred
before response headers; an earlier Deals timeout occurred during body reading.
A native connection/HTTP2 problem has not been proved or completely excluded.
Increasing a direct timeout is therefore not a demonstrated fix.

The implementation reduces exposure to those stalls with a short flight proof,
shared cooldown (instead of paying again for each endpoint), one recovery probe,
connection reuse and no nested retry loops. One redundant validation pass was
removed. Native DNS/connect/TLS/TTFB phase values remain unknown: diagnostics
measure send/read as a whole and do not invent phase precision.

## Matched final benchmark

Run on physical vin1 with the native production Python and release-local pinned
dependencies, loading the isolated committed SDK. All provider traffic ran under
`ndc-cert-call run`. Production source/config/serving files were not replaced.
The benchmark and recovery JSON have matching package hashes. The script records
body hashes and exact query bounds, never raw bodies, cookies or selectors.

`vin1-final.json`, generated by `vin1_probe.py`, retains every success and failure.
Two isolated calls per route compare the same builders/body hashes, US/USD,
one adult, JFK–LAX, 2026-11-30 shopping and Nov 1–30 calendar, separate tickets
excluded. Calendar direct returned 30 prices in 143.4 ms once and timed out once
at 2001.5 ms. Shopping direct timed out twice at about 2002 ms. The previous run
had two successful direct shopping calls at 356/413 ms; this variability is why
we do not claim a general direct speed advantage.

## Recovery and session/wire acceptance

`vin1-recovery.json` injects a single **local synthetic** timeout before the first
provider dispatch. It is labeled test control, not a Google failure. Actual mia1
returned 30 prices in 491.6 ms; the next call used only mia1 in 149.0 ms. After
waiting the real jittered cooldown, an actual native IPv6 request returned 30
prices in 227.0 ms and closed the primary circuit. No query/header/body rewrite
was used. Syscall evidence includes Google AF_INET6 and the actual mia1 proxy.

`vin1-sessions.json` records the earlier isolated session pass: genuine native
Deals success (30 deals, 3367.1 ms), native Explore timeout then actual mia1
rebootstrap/replay (87 destinations, 6062.0 ms total), hotel search/token, three
providers and ten reviews. Different Explore inventory counts do not establish
blocking by themselves; route health was opened for the actual timeout.

Hotels have no routing exception. Broad AtySUc returned usable hotels; M0CRd
returned gRPC 3 on the follow-up. This is separate unresolved wire triage, not
a not-applicable endpoint or a resolved provider limitation. Partial seed behavior
is preserved without claiming the rejected follow-up is fixed. Invalid arguments
do not poison route health.
A compact gRPC 13 or availability failure in an optional follow-up instead
restarts the full route session. Hotel follow-ups preserve explicit currency and
child ages instead of taking currency defaults from returned context.
